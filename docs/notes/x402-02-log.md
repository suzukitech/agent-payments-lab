# x402-02 作業ログ（2026-10-15、時系列）

一次情報: `@x402/fetch` / `@x402/core` 2.28.0 の d.ts と dist（`apps/paid-api/node_modules/@x402`）、https://github.com/x402-foundation/x402 の specs。生出力は `x402-02-run.md`。

1. **設計**: `apps/agent-client/src/buy.ts` の1ファイル。`x402Client` を手組みして `wrapFetchWithPayment` に渡す（フックを使うため。`wrapFetchWithPaymentFromConfig` ではフックを足せない）。新規依存なし（`@x402/*`、viem、tsx は paid-api と同じ版）。
2. **既定の上限が $1 だった**: `new x402Client()` だけで `spendControls.maxAmountPerPayment` は "$1"。第1回の `pay.ts` も気づかないまま $1 で守られていた。`buy.ts` は `setSpendControls({ maxAmountPerPayment: "$0.01" })` を明示（既定を下げる）。
3. **累計上限は SDK に無い**: `onBeforePaymentCreation` で `spent + amount > max-total` なら `{abort:true, reason}`、累計は `.x402-spend.json` に保存。加算は `onAfterPaymentCreation`（署名時点）にした。理由: 署名済みの認可は `validBefore` まで誰でも settle できる（後述 e）ので、署名＝最悪ケースの支払い確定として数える。副作用: 5xx で課金されなかった回も累計に入る（過大計上）。実際 b/b' 後の累計は 0.03 だが、支払われたのは a の 0.01 だけ。
4. **a. 200**: 買い手 19.99 → 19.98、tx 0xe431…ba2f。ただし `pnpm buy` 直後の残高読み取りは 19.99 のまま（公開 RPC への反映遅れ。次ケースの before で 19.98）。以降は run のあと 8 秒待ってから読むようにした。
5. **b. ハンドラが 500 を返す**: `PAYMENT-SIGNATURE` 付きの再送に対し 500 `{"error":"boom"}`、レスポンスに payment-* ヘッダーなし（`PAYMENT-RESPONSE` なし）。残高は前後とも 19.98、売り手も 0.02 のまま。**課金されない**（ソース確認の「status 400 以上は settle しない」と一致）。ただし verify を通ったあとハンドラまで走る分、500 でも 366ms かかる。
6. **b'. ハンドラが throw**: 500、ボディ空、payment-* ヘッダーなし、**課金されない**。Next の dev ログに `⨯ Error: boom at handler (app/api/throw/route.ts:6:9)`。つまり throw は `withX402` が握りつぶさず（exact では再 throw）Next 側の 500 になる。
7. **c. --max-per-call 0.005**: 1回目の 402 を受けたあと署名せずに throw（`All payment requirements were rejected by spendControls.maxAmountPerPayment ($0.005, ...)`）。spy に `PAYMENT-SIGNATURE` 付きリクエストは現れず、残高も不変。**署名前に止まる**。
8. **d. --max-total 0.02**: 1・2回目は 200（累計 0.02）、3回目は 402 を受けたあと `Payment creation aborted: max-total 0.020000 USDC would be exceeded (spent 0.020000 + 0.010000)` で停止。署名なし・残高 −0.02 のみ。`pnpm` を経由すると `buy.ts` の終了コード 2 は 1 に潰れる（`pnpm --filter ... buy` のラッパー）。コード 2 を見たいなら `tsx` を直接叩く。
9. **e. 想定外: 初回の settle が失敗**。`buy` が 402 のまま終了し、`PAYMENT-RESPONSE` は `success:false`、`invalid_exact_evm_transaction_failed`、メッセージ末尾に `Details: replacement transaction underpriced`（ファシリテーター側の送信ウォレットの nonce 衝突とみられる。こちらの原因ではない、推測）。この時点で買い手の残高は減っていない。**同じ `PAYMENT-SIGNATURE` を curl で再送したら 200 が返り、支払いが成立した**（`validBefore` 内ならそのまま使える＝署名は settle が成功するまで生きている、という推論が実機で裏付けられた）。ヘッダーは spy が出した JSON をコンパクトに再 base64 化して作った。
10. **e-2. 支払い済みの署名を再送**: 期待した `invalid_exact_evm_nonce_already_used` は**出なかった**。verify は通り、ファシリテーターが transferWithAuthorization を送信、`402` + `PAYMENT-RESPONSE`（`success:false`、`invalid_exact_evm_transaction_failed`、transaction あり）。そのトランザクションの receipt は `status 0x0`（オンチェーンで revert）。ガスはファシリテーター負担で、買い手の残高は動かない（二重払いにはならない）。nonce 使用済みの検知は `/verify` ではなく settle の revert で表面化した、というのが観測できた範囲。なぜ verify が通ったかは未調査。
11. **Vercel**: `npx vercel project protection` で `ssoProtection: all_except_custom_domains`、`protectionBypass` のシークレットが表示された（記録しない）。`npx vercel project protection disable paid-api --sso` で `ssoProtection: null`（ダッシュボード操作は不要）。
12. **Vercel の env が Preview のみ**: 第1回は `PAY_TO_ADDRESS` を Preview にだけ入れていたため、Production デプロイは `accepts[0]` に `payTo` が無い 402 を返していた。Production にも追加（アドレスは公開情報）。秘密鍵は入れていない。
13. **`.env.local` が上がる恐れ**: `apps/paid-api/.gitignore` は `.vercel` だけで、`.env.local`（`BUYER_PRIVATE_KEY` 入り）を `vercel` CLI がアップロードしうる。`apps/paid-api/.vercelignore` に `.env*` を追加して防いだ。
14. **dev は型を見ない**: `/api/throw` を `Promise<Response>` で書いて dev では動いたが、`vercel --prod` のビルドが `Promise<NextResponse>` を要求して 2 回失敗（TS2345）。`NextResponse` に直して Ready。
15. **公開 URL**: https://paid-api-flax.vercel.app （production alias）。外部からの `curl -i /api/weather` は 402 + `payment-required`、`pnpm buy` で 200（tx 0xac36…c2b2）。ローカルの dev と同じ見た目だが `resource.url` が公開ホストになる。
